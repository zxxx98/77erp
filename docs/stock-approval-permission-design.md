# 出入库统一审核与权限拆分设计

日期：2026-11-04

状态：审核范围与现有界面方案已确认，已按本文范围实施。

## 1. 目标

将“开单”和“审核记账”拆开。新增一个独立的 **出入库审核** 权限，普通出入库也必须先提交、后审核，审核通过才变动库存、库存成本和应收应付。

适用桌面 Web、移动 Web 和 PWA，三端使用同一服务端规则。管理员也必须执行提交和审核两个动作，不因身份或同时持有两类权限而自动通过。

示例：有“出库”权限的员工提交 10 件物料的出库单，库存暂不减少；有“出入库审核”权限的人员核对后通过，系统才扣减 10 件并生成有效账务。

## 2. 改造前实现与问题

- `shared/permissions.js`：`purchase` 同时覆盖入库开单、生产退料确认、成品入库审批；`sale` 同时覆盖出库开单和生产领料确认。
- `server/orders.js`：`createOrder` 保存普通单据后立即调用 `moveInventory`，没有待审核阶段。普通手工开单、二维码开单和 AI 开单共用此函数。
- `server/production-materials.js`：领料、补料、退料已有申请和确认流程，领补料支持分次实发；确认权限仍为对应方向的 `purchase` / `sale`。
- `server/production-receipts.js`：成品及入库废料按批次生成待入库单，`purchase` 可批准整单记账。
- `src/features/OrderApprovalWorkspace.jsx`：已有普通记录、成品待入库、退料待入库、领补料待出库分类，可沿用审核工作台结构。
- 当前普通单据查询仅识别 `active` / `void`；财务、仪表盘、操作历史、导出和通知均需检查，避免新增待审核单被当作有效业务。

## 3. 审核范围

以下是本次明确覆盖的范围，不允许通过切换开单入口绕过审核：

| 类型 | 提交后 | 审核通过后 |
| --- | --- | --- |
| 普通采购入库、普通销售出库 | 待审核，不变库存及账务 | 按原记账规则入库或出库 |
| 内部往来单位入库、出库 | 同普通单据 | 变动库存，仍不生成应收应付 |
| 二维码入库、出库 | 创建待审核单 | 按单据快照记账 |
| AI 预览确认生成的入库、出库，含批量开单 | 创建待审核单 | 由页面审核通过后记账 |
| 生产领料、补料 | 保留申请及剩余待发数量 | 每次审核实际发料数量并扣库 |
| 生产退料 | 保留待退料单 | 整单审核，增加库存并减少生产材料余额 |
| 生产成品及随批次入库废料 | 保留现有待入库单 | 整单审核，按快照增加数量与成本 |

**已确认范围：**本期仅对普通出入库、生产领料／补料／退料和成品入库实施上述审核。采购退货、销售退货、仓库调拨及撤销、盘点／库存增减、已记账单据作废（含已入库生产批次作废）保持现有流程、权限和记账时机，不新增审核申请，也不额外要求 `stock_approve`。

历史生产流程登记直接扣料、物料档案期初库存等其他库存入口保持现状；本期不将“出入库审核”扩大为全部库存变动审核。生产材料池内部耗用和半成品流转不属于仓库出入库，继续沿用现有规则。

## 4. 权限模型

新增权限键建议为 `stock_approve`，显示名为“出入库审核”。入库和出库共用一个审核权限，本期不再拆两个方向。

| 权限 | 调整后的职责 | 不再具备的能力 |
| --- | --- | --- |
| `purchase` 入库 | 手工／扫码／AI 入库提交，查看相应业务与申请结果 | 直接入库记账、生产退料及成品入库审核 |
| `sale` 出库 | 手工／扫码／AI 出库提交，查看相应业务与申请结果 | 直接出库记账、生产领补料审核 |
| `stock_approve` 出入库审核 | 查看授权仓库内所有本次范围内的待审核单及必要详情，审核通过、驳回／关闭待发余量 | 创建普通出入库单、生产申请或查看财务成本等额外能力 |
| `production` 生产管理 | 保留生产申请、登记和原有生产管理职责 | 不能仅凭生产权限审核领补料、退料及成品入库单 |
| `basic_view` 查看基础页面 | 保留现有只读范围，可查看单据状态和审核结果 | 提交和审核操作 |

规则：

1. 审核只要求 `stock_approve` 和对应仓库访问资格，不额外要求 `purchase`、`sale` 或 `production`。单独授予审核权限时必须可进入审核工作台及查看相关单据。
2. 审核权限不自动授予 `finance`；成本、毛利等字段继续按现有规则隐藏，不能通过审核接口泄露。
3. 普通出入库提交人和审核人记录用户 ID 与姓名快照；生产单据沿用现有操作人姓名快照。默认允许同一人同时拥有开单和审核权限并手动审核自己的单据；本期不增加“禁止自审”规则，也不增加多级审批。
4. 待审核普通单据允许提交人撤回；审核人可以驳回，均须填写原因。入库／出库权限本身不授予撤回他人单据的能力。
5. 生产申请人保留取消未完成申请的业务能力；审核人员可关闭未发余量。关闭不能撤销已经发出的库存。
6. 前端按钮、认证中间件、业务函数和幂等回放均检查当前权限。审核权限被撤销后，旧页面、旧请求及历史幂等响应不能成为继续审核的入口。
7. `production_only` 岗位继续隔离；审核权限只能在标准岗位中生效，不改变生产登记专用工作区规则。

## 5. 普通出入库状态与数据

普通单据沿用 `orders` / `order_items`，新增待审核生命周期，保留 `active` 表示“已审核且已记账”，以兼容现有有效单据查询。

| 状态 | 含义 | 可执行动作 |
| --- | --- | --- |
| `pending` | 待审核，尚未记账 | 审核通过、驳回、提交人撤回 |
| `active` | 已审核并记账 | 沿用已记账单据后续业务，作废保持现状 |
| `rejected` | 审核驳回，未记账 | 查看原因、复制为新单 |
| `cancelled` | 提交人撤回，未记账 | 查看记录、复制为新单 |
| `void` | 已记账后作废 | 查看原单和冲销记录 |

状态转换：`pending → active / rejected / cancelled`；`active → void` 沿用对应纠正规则。终态不能直接改回待审核，也不能删除审核痕迹。

本期不支持直接编辑待审核单据。填错后撤回并复制新单提交；驳回后复制重提，保留来源单 ID，重新生成单号和审核记录。

建议新增字段：

- 单头：`version`、`submitted_at`、`approved_at`、`approved_by`、`approved_by_name`、`rejected_at`、`rejected_by`、`rejected_by_name`、`reject_reason`、`cancelled_at`、`cancelled_by`、`cancelled_by_name`、`cancel_reason`、`source_channel`、`resubmitted_from_id`、`approval_origin`。
- 明细：补齐单位和数量取整规则快照；名称、条码、数量、单价、金额保留提交时快照。
- 待审核出库行尚无实际出库成本，使用 `NULL` 表达“未记账”，不得显示成零成本。入库金额可提前确定，但提交时不计入库存成本。
- `approval_origin` 区分 `workflow` 与 `legacy`。历史有效单据没有真实审核人时标注“历史已记账”，不得伪造审核时间或人员。
- 索引覆盖 `warehouse_id + status + type + submitted_at + id`。备份格式及校验同步支持新增状态、字段和关联。

提交时校验物料归属、启用状态、数量精度、单价、金额上限、往来单位及单位规则，生成唯一单号和待审核快照；库存只作为当时参考，不预留、不占用。库存不足的出库申请可以提交，界面提示“当前库存不足，审核通过前需补足”。审核时库存不足必须失败并保留待审核状态。

## 6. 审核与记账

普通单据整单审核，不做分次审批。审核通过时：

1. 在事务内检查当前审核权限、仓库访问资格、请求幂等键、单据 `version` 及 `pending` 状态。
2. 重新校验物料存在、归属、启用状态、单位及取整规则、往来单位有效性、数量与金额合法性。
3. 按最新实际库存校验出库量、入库后上限和成本安全性；出库成本按审核时的现有计价规则计算，不使用提交时估算成本。
4. 按提交时锁定的数量、单价及金额记账，审核人不能边审核边修改普通单据内容。单位等关键规则变化时拒绝通过，要求撤回或驳回后重提。
5. 在同一事务中更新库存、成本、单据状态、审核人、审核时间、版本及幂等结果。任一失败整单回滚，不能部分扣库。
6. 库存操作历史以审核记账时间为准，保留开单时间供查询。库存变动通知只在审核记账成功后触发，不能在提交时发送“已出库／已入库”。

并发规则：两个审核人只能有一个成功；审核和撤回竞争只能成功一个；不同单据竞争同一库存时按事务内实际余额判断，不能出现负库存。网络超时重试同一请求仅记账一次，权限检查先于幂等结果返回。

未审核、驳回、撤回单据不参与库存变动、有效采购销售额、应收应付、毛利、可退数量或收付款登记。审核完成后才允许原有财务及退货操作。报表区分开单时间与记账时间，业务发生额默认使用记账时间；历史单据以原创建时间兼容。

## 7. 生产流程兼容

- 保留生产材料单、逐次实发记录和成品入库单，不强行转换为普通采购销售单，避免重复记账和破坏材料池成本。
- 所有领补料 `confirm`、退料 `confirm`、成品入库 `confirm` 改为校验 `stock_approve`，不再用 `purchase` / `sale` 授权确认。相关列表及详情同步允许审核人员访问。
- 领补料继续按每次实发量审核。部分发料后申请仍可待发，但每次实发均记录独立审核人、时间、数量、成本与幂等结果；不得一次通过后让后续发料免审核。
- 保留现有允许按整袋超量发料的规则；审核界面明确区分申请量、本次实发量、累计实发量和超发量。
- 退料继续整单审核，审核时重查已领未耗余额；不能因提交时余额足够就在余额已经耗用后入库。
- 成品及入库废料继续随批次整单审核，登记和结束生产不等于已入库；未审核产量不显示为仓库可用库存。
- 材料单使用现有取消／关闭语义，不增加与部分实发冲突的整单驳回状态；关闭原因保留，已实发记录不回滚。待入库成品单不能脱离有效批次独立驳回或取消，需按现有批次作废流程处理。
- 现有生产单权限与登记范围不扩大。审核人只读审核必要的生产来源摘要，不能因此操作生产单。

## 8. 桌面、移动 Web 与 PWA

沿用项目当前的独立“入库”“出库”页面、桌面侧栏与顶栏、移动工作台及已有分类标签，不合并为新的“出入库”模块，不增加两层分类。保留现有蓝色选中标签、待办数量徽标、白色列表面板、搜索／状态筛选和“查看并审批”按钮样式。

- 入库页面分类：入库记录、普通入库待审核、成品待入库、退料待入库。
- 出库页面分类：出库记录、普通出库待审核、领料／补料待出库。
- 操作记录页面沿用现有汇总方向和分类，在对应方向补普通待审核分类。
- 普通记录中增加待审核、已审核、已驳回、已撤回、已作废状态筛选；待审核分类可查询处理历史，但徽标只计待处理数量。

默认入口：仅有开单权限时进入对应方向记录，仅有审核权限时进入对应方向普通待审核分类；同时拥有两类权限时保留现有记录默认入口，之后按 URL 恢复当前分类。页面标题继续使用“入库”或“出库”，原有“新建入库／新建出库”按钮位置不变。

桌面审核详情复用 `ProductionApprovalDialog` 和 `Modal` 的右侧抽屉，保留实际项目的遮罩、宽度、标题与关闭按钮，不能替换为整页详情或重新绘制一套页面。手机复用同一组件现有全屏弹层及返回行为。普通审核列表复用 `ProductionApprovalList` 的行间距、单号、状态徽标和操作布局。

待审核列表每页十条，显示单据类型及单号、往来单位或生产单号、提交人及时间、物料摘要及数量、状态。列表不直接提供通过按钮，点击“审核”打开完整详情，核对后再操作。不做批量审核。

普通单据详情按“状态及来源 → 仓库和往来单位 → 提交人和时间 → 物料明细 → 当前库存与预计变动 → 审核操作”排列。仅显示明细物料各自的数量和单位，不跨单位汇总库存。通过前再次确认实际方向和数量；库存不足时标明缺口，通过操作失败后仍保留待审核单。

手机端列表改为紧凑卡片，分类允许换行，详情占满页面；审核按钮固定在详情底部安全区，内容预留底部空间，驳回按钮为次要操作。驳回弹出必填原因表单；审核通过后返回原分类并刷新待办数。生产领补料详情继续保留本次实发数量输入，退料及成品整单核对。

岗位权限配置中，“入库”“出库”“出入库审核”分别为独立勾选项。“入库／出库”说明改为提交对应单据；“出入库审核”说明列出普通单据和生产领补退料、成品入库，不包含调拨、盘点、退货及作废。

- 开单按钮改为“提交审核”；成功提示“已提交，等待审核，库存尚未变动”，展示单号及详情入口。持有审核权限也不自动通过。
- 审核详情显示来源、仓库、往来单位、提交人、提交时间、物料快照、当前库存与预计变动；有权限时显示审核按钮和必要金额，成本展示仍遵循财务权限。
- 普通单据提供“审核通过”“驳回”；生产材料单提供“审核发料／审核退料”和“关闭／取消”，成品提供“审核入库”。所有通过动作均显式二次确认。
- 桌面使用现有抽屉，手机使用全屏详情；保留分页、搜索、错误重试及 URL 分类恢复。处理成功后刷新库存、详情、列表和待审核计数；处理失败保留界面并显示具体原因。
- 仅有审核权限的用户可进入工作台；仅有开单权限的用户可查看相应单据进度，不显示审核动作。已有生产详情跳转继续跳到对应分类。
- PWA 本地草稿与“提交结果待核实”继续独立存在，不得与服务端 `pending` 业务状态混用。在线确认提交成功后才删除本地草稿；结果不明时按原幂等键核查。
- 离线可保存草稿，审核必须在线。升级后旧客户端请求也只能创建待审核单；PWA 发布同步更新缓存版本及结果文案，避免将提交成功误报为出入库完成。
- 新增及调整文案同步中文、英文、越南文；Android 浏览器、iOS Safari 和 PWA 使用同一规则。

## 9. 服务端与 AI 助手

建议接口契约：

| 接口 | 行为与授权 |
| --- | --- |
| `POST /api/orders` | 保留入参结构及方向开单权限，返回 `{ id, number, status: 'pending', version }`，不变库存 |
| `GET /api/orders` / `GET /api/orders/:id` | 支持新状态和审核元数据；审核人员可读取授权仓库内必要详情 |
| `POST /api/orders/:id/approve` | `stock_approve`，携带 `version` 和幂等键，整单记账 |
| `POST /api/orders/:id/reject` | `stock_approve`，携带版本、幂等键和原因，不变库存 |
| `POST /api/orders/:id/cancel` | 当前提交人及相应方向权限，携带版本、幂等键和原因，不变库存 |
| 既有生产材料／入库 `confirm` | 保留参数及分次语义，确认授权切换为 `stock_approve` |

校验失败返回明确业务原因；无权限 `403`，跨仓库／不可访问单据 `404`，版本或状态冲突 `409`。认证路由白名单和业务层同时更新，不能只改按钮或中间件。

将 `createOrder` 拆成提交待审核单与审核记账两项职责，让普通接口、二维码和 AI 共用提交逻辑，记账入口只能在审核操作后调用。生产沿用现有独立账本和事务。

二维码扫码确认只代表“提交待审核”，与审核通过分开。扫描次数在成功创建待审核单时消耗，驳回／撤回不自动返还，网络重试不重复消耗。提交时固定二维码版本和单据内容，后续修改或停用二维码不修改已提交单据。

AI 同步要求：

- 更新 `server/ai.js` 的工具说明、权限校验、预览、执行结果和查询状态；`preview_orders` 的用户确认只创建待审核单，不算审核。
- 更新 `src/AiAssistant.jsx` 的动作卡片和结果文案，明确“提交后不变库存”“预计库存仅供参考”，不能显示已完成出入库。

## 11. 实施拆分与验收

建议按“权限及迁移 → 普通提交／审核记账 → 生产授权切换 → 桌面与移动界面 → AI／二维码／报表兼容 → 验证”顺序实施。

关键验收：

1. 普通入库／出库无论来自手工、二维码还是 AI，提交成功库存与成本均不变；审核成功恰好变动一次。
2. 只有入库／出库权限不能审核；只有审核权限可审核两个方向，不能开单、登记生产或查看受限财务字段。
3. 同时具备开单和审核权限及管理员开单均进入待审核，自审必须再次明确执行审核。
4. 驳回／撤回不变库存，无收付款、可退数量或有效业务汇总；复制重提保留原单记录。
5. 领补料分次、超量发料、关闭余量、退料余额竞争、成品及废料整单入库继续符合现有规则，本次范围内的实际入出库动作检查审核权限。
6. 审核时库存不足、单位改变、物料启停状态变化、金额溢出均整单失败；并发通过／撤回、重复请求及超时重试无重复记账。
7. 跨仓库访问、权限实时撤销、旧幂等响应、仅审核岗位入口及生产专用岗位隔离均通过 API 验证。
8. 审核前后库存、平均成本、财务、仪表盘、操作历史、导出、通知与数据刷新一致，审核日期与开单日期跨日时也正确。
9. 历史有效单据和既有生产待处理单正确迁移，备份恢复保留新状态，重复迁移不重复记账。
10. 调拨及撤销、盘点增减、采购／销售退货和已记账单据作废仍按原权限和流程直接处理，不因本次新增审核权限而被阻止；仅有审核权限也不能执行这些操作。
11. 桌面、移动 Web、Android 浏览器、iOS Safari 及 PWA 验证开单→待审核→审核→结果刷新；覆盖离线草稿、提交结果不明、返回键及旧缓存更新。
