# 商品二维码协议

商品条码页面默认显示 CODE 128，右上角可切换二维码并下载 SVG。二维码使用 UTF-8 JSON，四模块留白及 M 级纠错。二维码在本地生成，不向第三方传输商品信息。

## 第一版数据格式

```json
{
  "format": "77erp",
  "version": 1,
  "type": "product",
  "source_id": "708528e6-7d1e-4d1b-8ba3-f4f769931c49",
  "warehouse_id": 1,
  "product": {
    "id": 12,
    "barcode": "SKU-000012",
    "name": "马克杯",
    "unit": "个"
  }
}
```

`format` 为协议标识，`version` 为结构版本，`type` 为数据类型。`source_id` 是数据库首次启动时生成、后续保持不变的 UUID，通过 `/api/data` 的 `instance_id` 获取，不受域名或服务器地址变更影响，也不是认证凭据。`warehouse_id` 和 `product.id` 标识该来源数据库的仓库及商品，`barcode` 用于核对编码。跨服务器使用时必须明确建立映射，不得仅凭编号匹配。名称和单位是打印时的展示快照，应以服务器当前商品资料为准。

重置业务数据及恢复业务备份保留当前数据库的来源标识；完整复制数据库会保留原来源标识。将业务备份导入一个新数据库后，旧标签需重新生成或显式映射来源。即使来源一致，未来扫描器也必须校验当前商品编码与编号，避免重置后编号复用导致误识别。

二维码不包含库存、价格、账号、服务器凭据、数量或执行指令。商品修改后重新下载可更新标签内容；旧标签保留生成时的快照。无需为每个商品存储二维码图片或增加另一个商品编码。

## 后续扫码入库的扩展边界

本次仅实现二维码展示、切换和下载，现有扫描流程保持原样，尚未解析此协议或新增入库操作。

未来解析器应先区分普通条码与本协议，验证标识、版本和类型，拒绝不支持的版本及类型。`product` 类型只用于识别商品，不能因扩展字段出现而执行库存操作。解析时必须核对当前服务器、仓库、商品编号和编码，不信任二维码中的名称、单位、价格等快照。

未来的入库数据应定义独立类型（例如 `stock_receipt`）及明确的单据结构，包含来源标识、唯一业务编号、目标仓库、商品明细和数量，并约定版本兼容规则。扫码后仍需服务器校验权限、仓库归属和商品资料，通过唯一业务编号保证重复扫描不会重复入库，复用现有入库事务创建单据与变更库存。若支持一键入库，需单独定义用户确认和错误反馈流程；不能将任意 JSON、URL 或商品标签当成执行命令。本次不实现该类型、解析器或业务接口。
