# 物料二维码协议

物料条码页面默认显示 CODE 128，右上角可切换二维码并下载 SVG。二维码使用 UTF-8 JSON，四模块留白及 M 级纠错。二维码在本地生成，不向第三方传输物料信息。

## 第一版数据格式

```json
{
  "format": "77erp",
  "version": 1,
  "type": "product",
  "source_id": "708528e6-7d1e-4d1b-8ba3-f4f769931c49",
  "warehouse_id": 1,
  "product": {
    "id": 12,
    "barcode": "SKU-000012",
    "name": "马克杯",
    "unit": "个"
  }
}
```

`format` 为协议标识，`version` 为结构版本，`type` 为数据类型。`source_id` 是数据库首次启动时生成、后续保持不变的 UUID，通过 `/api/data` 的 `instance_id` 获取，不受域名或服务器地址变更影响，也不是认证凭据。`warehouse_id` 和 `product.id` 标识该来源数据库的仓库及物料，`barcode` 用于核对编码。跨服务器使用时必须明确建立映射，不得仅凭编号匹配。名称和单位是打印时的展示快照，应以服务器当前物料资料为准。

重置业务数据及恢复业务备份保留当前数据库的来源标识；完整复制数据库会保留原来源标识。将业务备份导入一个新数据库后，旧标签需重新生成或显式映射来源。即使来源一致，扫描器也会同时校验当前物料编号与编码，避免重置后编号复用导致误识别。

二维码不包含库存、价格、账号、服务器凭据、数量或执行指令。物料修改后重新下载可更新标签内容；旧标签保留生成时的快照。无需为每个物料存储二维码图片或增加另一个物料编码。

## 物料与业务二维码的分流

网页与安卓扫码工作台先按协议类型分流。`product` 类型只定位物料，仍核对来源标识、当前仓库、物料编号和条码；任一不符时明确报错。入出库表单和物料编辑只接受普通条码或物料标签，不接受业务二维码。物料编辑中扫描标签只取其中条码。名称、单位快照及额外执行字段不能使物料标签触发库存操作。

## 出入库业务二维码

业务二维码采用独立的 `stock_operation` 类型，同样使用协议版本 1：

```json
{
  "format": "77erp",
  "version": 1,
  "type": "stock_operation",
  "source_id": "708528e6-7d1e-4d1b-8ba3-f4f769931c49",
  "warehouse_id": 1,
  "qr_id": "a08f04e0-6420-4c84-9c07-189e70c95539"
}
```

`qr_id` 为服务端配置的随机公开标识，不是登录凭据。物料组合、各行数量及成交单价、累计次数上限、往来单位和确认开关均保存在服务器，不信任二维码中的额外配置字段。编辑保留标识，原标签读取最新规则。每个二维码对应当前仓库 1–100 条物料明细，同一物料不能重复，全部按同一方向执行。

只有扫码工作台中匹配操作方向的入库/出库模式可执行。服务端预览返回完整单据内容与短期 token，默认需用户确认；关闭确认后，主动扫码直接提交整单。执行在同一事务中创建一张单据、更新全部物料库存和成本、消耗一次额度并保存使用记录。失败和取消不计次；token 和用户级请求标识避免网络重试重复开单。二维码不能代替登录、仓库归属或开单权限校验。

旧客户端会拒绝该新类型。业务备份恢复时全部配置停用并重新生成标识，旧标签失效；重新核对、启用后需要重新打印。详细规则、接口与多物料编辑流程见 [出入库二维码编辑功能设计](stock-operation-qr-design.md)。
