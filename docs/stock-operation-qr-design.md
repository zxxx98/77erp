# 出入库二维码编辑功能设计

状态：已按本设计实现服务端、Web 和 Android 源码。日期：2026-10-13。

## 1. 目标与范围

新增独立的「入库二维码」和「出库二维码」，支持创建、编辑、启停、查看使用记录和下载标签。一个二维码可配置多个商品，扫码时按整组明细生成一张采购入库或销售出库单，并一起更新当前仓库中所有关联商品的库存。

核心配置为「每个商品的单次数量」「整码可扫描次数」「整单需要二次确认」，二次确认默认开启。配置保存在服务端，二维码只携带来源与配置标识，编辑后已打印的标签使用最新配置。

本草案采用以下产品默认值，作为后续实现依据：

- 每个二维码包含当前仓库的 1–100 条商品明细，同一商品不能重复，可为同一商品或商品组合建立多个二维码。
- 每条商品明细的单次数量默认 1，可扫描次数默认 1，也可选择「不限次数」。
- 一次扫码统一执行全部商品，生成一张单据、消耗一次额度；任一商品校验或执行失败，整笔回滚。
- 管理员管理二维码，管理员和员工均可扫码执行，沿用现有开单权限。
- Web 与 Android 都支持配置和扫码；Web 提供 SVG 标签下载，Android 提供二维码展示。

全部明细使用同一个仓库、操作类型和往来单位，统一入库或统一出库。本期不包含同码混合入库与出库、跨仓库操作、仓库调拨、退货二维码、离线执行、外部系统扫码执行、批量生成及二维码有效期配置。普通条码和现有商品二维码继续用于识别商品。

## 2. 现状与接入原则

现有 `docs/product-qr.md` 定义 `type: product` 标签，Web 和 Android 会校验来源、仓库、商品编号与条码后定位商品。扫码工作台的入出库模式会打开普通开单表单，表单扫码每次增加 1 件，不直接修改库存。

服务端 `POST /api/orders` 已支持单据与库存事务、移动加权平均成本、创建人记录以及按用户隔离的 `request_id` 幂等保护。员工可开单，但新增接口默认仅管理员可用。新增功能前业务备份为版本 6，本功能升级为版本 7。

新功能使用独立二维码类型和执行接口。商品标签上的额外字段不能触发出入库；新业务类型也不能被商品编辑、普通开单或查找商品入口降级解释成商品标签。

## 3. 配置字段与规则

| 字段 | 默认值 | 规则 |
| --- | --- | --- |
| 二维码名称 | 入库二维码 / 出库二维码 | 必填，1–60 字，可自定义组合名称；从商品入口新建时初值为商品名称 + 入库/出库 |
| 操作类型 | 按入口选择 | `in` 入库、`out` 出库；创建后不可修改，改变用途应新建 |
| 仓库 | 当前仓库 | 创建后不可修改，全部商品必须属于该仓库 |
| 商品明细 `items` | 从商品入口预填该商品；管理入口为空 | 保存时必须有 1–100 条，商品不能重复；支持添加、移除及调整顺序 |
| 每条明细数量 `items[].quantity` | 1 | 每个商品每次执行的数量，正整数，1–99,999,999，单位沿用该商品 |
| 可扫描次数 `max_scans` | 1 | 指累计成功执行上限；有限次数为 1–99,999,999，「不限次数」保存为 `null` |
| 需要二次确认 `require_confirmation` | `true` | 两端表单显式提交布尔值；创建接口省略时由服务端设为 `true`，编辑接口必须提交，不能将缺失值解释为关闭 |
| 每条明细成交单价 `items[].price_cents` | 添加商品时采购/销售参考价 | 每个商品独立保存固定成交价，以分保存；非负整数，范围沿用现有开单限制 |
| 往来单位 | 出库「零售客户」，入库留空 | 入库保存前必须填写；沿用现有供应商/客户选择和名称新建规则 |
| 单据备注 | 空 | 最多 500 字，每次生成单据时使用此备注 |
| 启用 `enabled` | `true` | 停用后仍可查看配置和历史，但不能执行 |

数量表示**该商品一次成功执行的数量**，不是整码总数量。配置「商品 A：5 个、商品 B：2 箱」，可扫描次数为 3，则每次同时处理 A 5 个与 B 2 箱，最多生成 3 张含两条明细的单据，累计处理 A 15 个、B 6 箱。不同商品的数量和单位分别展示，不直接相加。

添加商品时的参考价只是该行的表单初值；保存后使用各行配置中的固定价格，商品参考价变化不会自动修改二维码成交价。商品名称可显示最新值；任一商品条码或计量单位变化后，拒绝执行整组配置，管理员需核对并重新保存，使各行商品条码、单位快照与当前档案一致。

管理员可编辑组合内的商品及各行数量、价格，但不能移除全部明细。整组明细与配置在同一事务中保存，并递增同一个配置版本，使已有预览失效。保存前提示「修改后，已打印的二维码将按新的商品明细执行」；审计保存完整修改前后版本，历史单据和使用记录保留当时的明细。修改组合不重置已用次数。

往来单位在二维码配置保存时按操作类型校验、解析或创建，保存编号和名称快照。执行时使用当前有效的关联往来单位；停用后阻止执行，改名后返回最新名称供预览。用户确认期间名称变化须重新预览。金额和往来单位完整后，关闭二次确认才有明确、可执行的单据内容。

### 次数语义

- 只在整张单据创建、全部商品库存及成本变更提交成功后增加一次 `used_scans`，不按商品条数或件数计次。
- 识别、预览、取消、失败、网络重试命中原结果均不计次。
- 同一二维码在不同设备、不同用户之间共享额度；下载多份标签不会增加额度。
- 有限次数的剩余值为 `max_scans - used_scans`，不限次数显示「不限」，同时展示已用次数。
- 编辑次数上限不重置 `used_scans`，新上限不得小于已用次数；等于已用次数表示已用完。提高上限后可继续使用。
- 已用完、停用、配置失效分别显示原因。不限次数也必须校验计数安全范围，超出安全整数范围时拒绝执行。
- 作废或退货沿用现有业务纠正流程，不返还次数，使用记录仍关联原单据并展示其当前状态。

## 4. 页面与交互

### 4.1 管理入口

在商品标签页面增加「出入库二维码」入口，与现有「条形码 / 商品二维码」区分；该入口列出包含当前商品的配置，新建时预填该商品，允许继续添加其他商品。在扫码工作台增加管理员可见的「管理出入库二维码」，方便查看当前仓库全部配置并新建商品组合。Android 商品详情和扫码工作台提供对应入口。

列表显示名称、商品摘要与商品种数、操作类型、已用/上限、二次确认状态及可用状态；展开后查看各商品单次数量与单位。支持按包含的商品、操作类型和状态筛选，提供「新建」「编辑」「启用/停用」「查看记录」「查看标签」。第一期保留配置，不提供物理删除；仍被当前二维码明细引用的商品不能删除，需下架或先从配置中移除，商品删除校验增加明细关联检查。

### 4.2 编辑页面

表单依次展示：基本信息 → 商品明细 → 次数与二次确认 → 往来单位与备注 → 标签预览。

- 商品明细支持搜索、扫描普通条码或商品二维码来添加当前仓库商品；重复添加定位已有行，不新增重复行，也不静默修改数量。
- 每行展示商品名称、编码、单位、当前库存，分别填写单次数量和成交单价，并显示行金额；允许移除或调整顺序。Web 使用明细表，Android 使用明细卡片；达到 100 条时禁止继续添加。
- 数量输入框旁显示该行商品单位；二维码级次数提供「限制次数 / 不限次数」，限制模式下显示整数输入框。
- 编辑时显示「已使用 2 次」，并说明次数上限是累计上限。
- 「需要二次确认」开关默认开启；关闭时显示说明：「扫码后将直接生成单据并更新库存。」
- 显示每行金额、单据总金额、各商品当前库存及按当前配置计算的剩余可执行数量（每行数量 × 剩余次数）；不限次数不展示剩余可执行数量。该值仅供展示，不预占库存，不合并不同单位的数量；历史累计量按使用记录中的实际明细统计，不能用修改后的数量反推。
- 入库即使商品库存为 0 也可创建；出库任一商品库存不足可以保存配置，但标记对应明细并提示当前无法整组执行。
- 二维码只在首次保存成功后可下载；有未保存修改时先保存，再下载带有最新说明文字的标签。
- 提交期间锁定操作，失败保留输入；多人编辑采用配置版本校验，冲突时提示刷新，避免覆盖。

标签包括二维码、组合名称、仓库、入库/出库、商品种数、各行商品名称/编码/数量/单位及确认方式。SVG 按明细条数自适应高度，二维码保留固定清晰尺寸；Android 展示支持滚动查看完整明细。次数不印动态剩余额度；标注「以系统当前配置为准」。编辑商品组合、数量、次数、确认方式无需重印二维码，但纸面说明可能已过时，应建议重新下载标签。

### 4.3 扫码入口分流

| 入口 | 普通条码 / 商品二维码 | 出入库二维码 |
| --- | --- | --- |
| 工作台「查找商品」 | 定位商品 | 提示切换到对应入库/出库模式，不执行 |
| 工作台「扫码入库」 | 打开普通入库表单 | 仅接受入库二维码，走专用执行流程 |
| 工作台「扫码出库」 | 打开普通出库表单 | 仅接受出库二维码，走专用执行流程 |
| 普通开单表单 / 模板 | 增加商品，沿用原行为 | 提示到扫码工作台执行，不能混入未提交单据 |
| 商品编辑扫码 | 提取商品条码 | 明确拒绝，不能填入二维码标识 |

模式和二维码用途不一致时说明「这是出库二维码，请切换到扫码出库」，不得自动改模式或执行相反操作。仓库不一致时提示用户切换后重新主动扫码，不自动切换仓库。

### 4.4 二次确认开启（默认）

1. 用户主动开启扫描，识别成功后立即停止本轮识别。
2. 服务端预览校验并返回待执行内容，不扣次数、不锁库存。
3. 显示「确认入库 / 确认出库」弹窗，展示仓库、完整商品明细（每行数量、单位、成交单价、行金额与库存）、总金额、往来单位、备注及剩余次数。明细较多时可滚动查看，统一确认整张单据。
4. 用户点击确认后提交；成功显示单号、实际执行明细和最新剩余次数，并刷新全部关联商品库存。
5. 取消或关闭弹窗不生成单据、不扣次数。

确认页内容为只读，不支持只勾选部分商品执行。调整本次商品、数量、价格或往来单位应取消并使用普通开单；修改后不能继续套用该二维码的次数额度。

### 4.5 二次确认关闭

扫码入口显示「免确认二维码将直接执行全部商品」说明。用户主动扫描后，客户端先获取服务端预览，确认当前配置为免确认，再立即提交整组执行，不再显示确认弹窗。成功与失败均显示明确结果，不能跳过失败商品只执行剩余明细。

关闭仅跳过用户弹窗，服务器仍校验身份、权限、来源、仓库、配置版本、额度和库存。执行后不自动恢复摄像头；用户需点击「继续扫码」开始下一次，从而避免同一画面连续生成单据。Web 和 Android 均采用一次主动扫描对应一次执行请求。

## 5. 二维码协议

沿用 `format: 77erp`、UTF-8 JSON、M 级纠错与四模块留白，增加独立的 `stock_operation` 类型：

```json
{
  "format": "77erp",
  "version": 1,
  "type": "stock_operation",
  "source_id": "708528e6-7d1e-4d1b-8ba3-f4f769931c49",
  "warehouse_id": 1,
  "qr_id": "a08f04e0-6420-4c84-9c07-189e70c95539"
}
```

`qr_id` 为随机 UUID，是服务端配置的公开查询标识；它不是登录凭据或匿名执行授权。二维码不携带数量、次数、价格、确认开关或执行 URL，客户端和服务端均拒绝用扩展字段覆盖配置。

`version` 表示该类型的协议结构版本，配置版本由服务器单独返回，不印入二维码。编辑保留 `qr_id`，旧标签查询最新配置；新建配置使用新 `qr_id`。

解析流程先校验标识和协议版本，再按类型分流。旧客户端会拒绝新类型，需升级后才能使用；服务器不支持时提示功能不可用。其他来源、其他仓库、无效 UUID、未知类型均明确报错，不能降级为可执行命令。

## 6. 数据模型

新增 `server/stock-qr.js` 承载迁移、配置校验和接口。以下为逻辑字段，实施时细化建表与索引：

| 表 | 主要字段 | 用途 |
| --- | --- | --- |
| `stock_qr_codes` | `id`、唯一 `qr_id`、`warehouse_id`、`name`、`type`、`max_scans`、`used_scans`、`require_confirmation`、`partner_id`、`partner_name`、`note`、`enabled`、`version`、创建/更新人及名称快照、时间 | 二维码级配置及累计成功次数 |
| `stock_qr_items` | `id`、`stock_qr_id`、`product_id`、`product_barcode`、`product_unit`、`quantity`、`price_cents`、`sort_order` | 当前商品明细，配置与商品联合唯一，商品关联用于删除校验 |
| `stock_qr_revisions` | `id`、`stock_qr_id`、`version`、配置快照 JSON、操作人及名称快照、时间 | 创建、编辑、启停的审计记录，每个配置版本唯一 |
| `stock_qr_usages` | `id`、`stock_qr_id`、`config_version`、`order_id`（唯一）、`scan_number`、含完整明细的执行配置快照、执行人及名称快照、`created_at` | 一次整组成功执行对应一条使用记录，配置与 `scan_number` 联合唯一 |
| `stock_qr_previews` | `id`、唯一 `token_hash`、`stock_qr_id`、`config_version`、`user_id`、`warehouse_id`、单据内容快照、`expires_at`、`order_id`、`response` | 短期预览凭据，绑定用户及配置，单个凭据最多生成一张单据 |

布尔字段使用 `NOT NULL DEFAULT 1` 和 0/1 约束。明细数量、额度及已用次数同时设置服务端与数据库约束；1–100 条明细与同仓库限制在保存事务中校验，建立配置仓库索引、明细商品索引、配置/时间使用记录索引。商品组合替换、配置更新与版本审计在同一事务中完成，不允许保存半组明细。`version` 只在配置或任一明细变化时递增，扣次数不递增，避免不同用户正常扫码互相产生配置冲突。

预览 token 使用不可预测的随机值，仅保存哈希，5 分钟有效，过期且未执行的记录在预览时清理；已成功执行的凭据保留原响应以支持重试，不保存二维码图片。审计和使用记录保存快照，以免编辑配置后改变历史含义。

## 7. 接口设计

全部接口需登录，沿用 `X-Warehouse-ID` 和现有写请求来源检查。接口显式校验配置与商品的仓库归属，不能仅依赖当前仓库中间件已有的 URL 匹配规则。

| 接口 | 权限 | 说明 |
| --- | --- | --- |
| `GET /api/stock-qrs` | 管理员 | 当前仓库列表，支持筛选与分页 |
| `POST /api/stock-qrs` | 管理员 | 新建，提交完整 `items` 数组，服务端补齐默认值，支持 `request_id` 防重复创建 |
| `GET /api/stock-qrs/:qr_id` | 管理员 | 配置详情 |
| `PUT /api/stock-qrs/:qr_id` | 管理员 | 编辑或启停，必须带 `version` 和完整 `items` 数组，一次替换整组配置；支持 `request_id` |
| `GET /api/stock-qrs/:qr_id/usages` | 管理员 | 分页使用记录，关联单据当前状态 |
| `GET /api/stock-qrs/:qr_id/revisions` | 管理员 | 分页配置修改记录 |
| `POST /api/stock-qrs/preview` | 管理员、员工 | 传入扫码协议内容与当前 `mode`，仅校验并创建短期预览 |
| `POST /api/stock-qrs/:qr_id/execute` | 管理员、员工 | 传入预览 token、确认标志及 `request_id`，执行单次出入库 |

创建/编辑的 `items` 结构示例（其他配置字段在请求顶层）：

```json
{
  "items": [
    { "product_id": 12, "quantity": 5, "price_cents": 2400 },
    { "product_id": 18, "quantity": 2, "price_cents": 3500 }
  ]
}
```

数组顺序作为展示和单据明细顺序；每个商品编号均需独立校验归属，空数组、超过 100 条及重复商品均拒绝。预览返回 `preview_token`、`expires_at`、配置 `version`、操作类型、仓库、完整 `items` 数组（每行商品编号、名称、编码、单位、数量、成交单价、行金额、当前库存）、总金额、往来单位、备注、`used_scans`、`max_scans`、`remaining_scans` 与 `require_confirmation`。不限次数的剩余值为 `null`。预览不是额度或库存预留，最后一次额度可能被其他设备先使用。

执行请求示例：

```json
{
  "preview_token": "opaque-random-token",
  "confirmed": true,
  "request_id": "client-generated-unique-id"
}
```

二次确认开启时必须显式提交 `confirmed: true`；免确认流程提交 `false`。服务端从当前配置判断是否允许。确认标志是应用流程约定，无法证明用户在屏幕上点击过；二维码本身不能解除登录和开单权限。

成功返回单据 `id`、`number`、实际执行 `items` 明细、总金额、最新已用次数和剩余次数。新执行返回 201，幂等重试返回原结果。库存或商品校验失败时，在错误响应中附带失败商品编号、名称及逐行原因，方便定位问题。员工预览与执行响应沿用普通开单的数据可见范围，不附带收付款详情、管理审计或其他用户的使用记录。

错误响应增加稳定 `code`，供两端统一处理：

| 状态 | 示例错误码 | 客户端行为 |
| --- | --- | --- |
| 400 | `INVALID_QR`、`SOURCE_MISMATCH`、`WAREHOUSE_MISMATCH`、`MODE_MISMATCH` | 显示原因，不执行 |
| 401 / 403 | 登录失效 / 无权限 | 沿用登录和权限处理 |
| 404 | `QR_NOT_FOUND` | 提示配置不存在或标签已失效 |
| 409 | `CONFIG_CHANGED`、`QR_DISABLED`、`SCAN_LIMIT_REACHED`、`PRODUCT_CHANGED`、`PARTNER_CHANGED`、`STOCK_INSUFFICIENT` | 保留错误原因；需重新预览、扫码或修正配置，不能静默执行 |
| 409 | `CONFIRMATION_REQUIRED`、`PREVIEW_EXPIRED`、`REQUEST_CONFLICT` | 返回对应原因，重新进入明确的操作流程 |

免确认流程遇到冲突也停止，由用户主动重新扫码。特别是管理员在预览后开启二次确认时，服务器必须拒绝旧免确认请求，并让客户端展示最新配置的确认流程。

## 8. 执行事务、并发与重试

从 `server/app.js` 的普通开单处理抽取内部单据创建函数，负责商品与金额校验、单号、往来单位、明细、库存和成本变更。普通开单和二维码执行共享该逻辑；函数接受外层事务，不自行嵌套事务，也不通过 HTTP 再调用 `/api/orders`。

二维码执行使用单个 `BEGIN IMMEDIATE` 事务：

1. 校验当前登录用户、开单权限和当前仓库；查询按用户隔离的 `request_id`。完全一致且已成功的请求直接返回历史响应。
2. 校验预览 token 哈希、用户、仓库和二维码绑定。若该 token 已执行，返回其原单据结果，不再扣额度；需要另做一次业务必须重新主动扫码获取新 token。
3. 未执行 token 必须未过期，配置仍启用，预览配置版本与当前版本一致，来源、模式及仓库正确，全部商品条码/单位和往来单位仍符合快照，确认方式有效。
4. 从服务器配置与完整明细组装单据，不接受执行请求提交的商品、数量、单价或确认策略；重新校验额度、每行商品的库存与金额、单据总金额安全范围。
5. 创建一张普通采购/销售单据及全部明细，逐商品变更库存与成本。开单人为实际扫码用户，而非二维码创建人。
6. 带额度条件增加 `used_scans` 并检查影响行数，写入唯一使用记录，将预览标记为已执行，保存幂等响应。
7. 全部成功后提交；任一商品或步骤失败则整笔回滚，全部商品库存与成本均不变、不生成单据、不扣次数、不保留成功使用记录。不能拆单、部分执行或跳过缺货商品。

只有一次额度时，两台设备分别预览、同时提交，最多一个成功，另一个返回额度已用完。两台设备同时出库，即使预览均显示库存足够，也以事务中的实时库存为准，不能出现负库存。

摄像头识别回调需使用同步锁，识别第一帧即停止相机，避免停止过程中的重复回调创建多个 token。提交按钮同样锁定；不限次数配置也遵循此规则。

客户端在发送执行请求前保存 token、`request_id` 和完整请求，按服务器、账号及仓库隔离。网络超时或应用中断导致结果未知时，重试同一个请求，不重新取 token 或生成新 `request_id`。已提交成功的请求即使之后 token 过期、二维码停用或配置被修改，仍返回原单据，避免重复开单。恢复未知请求前，当前用户和仓库必须匹配。

收到明确未执行的业务错误后可结束该请求；重新预览产生新的 token 和操作标识。成功后先记录执行完成，再刷新业务数据；刷新失败只提示刷新失败，不能重新提交已成功的业务。原单据后来作废时重试仍指向原单据，不能重新生成一张。

## 9. 权限、迁移与备份

- 在 `server/auth.js` 的员工白名单中仅增加预览和执行接口；配置列表、详情、修改、记录管理保持管理员权限。管理入口仅管理员可见。
- 员工执行时重新检查身份与权限，二维码不作为授权依据，不提供匿名扫码接口。
- 数据库迁移新增表和索引，已有商品标签及单据不变；新配置默认需要确认。配置修改、启停与审计写入同一事务。
- `server/warehouses.js` 与新接口增加配置归属和商品归属校验，阻止跨仓库编号引用。
- 业务备份升级到版本 7，包含配置、全部商品明细、版本审计和成功使用记录，保留已用次数与单据关联；恢复校验每组明细数量、商品唯一性、仓库归属及快照。兼容版本 1–6，旧备份对应二维码表为空。预览凭据与请求重试缓存不进入业务备份。
- 业务恢复覆盖当前二维码相关数据。所有恢复的配置重新生成公开 `qr_id` 并设为停用，保留内部关联及已用次数；管理员核对后启用并重新打印。如此可防止旧快照把已使用的二维码额度恢复成可再次执行。跨服务器恢复清除用户编号关联，保留操作人名称快照，沿用现有恢复规则。
- 重置业务数据清空配置、商品明细、审计、使用记录、预览及请求缓存，按外键依赖顺序删除；保留现有账户及系统配置。旧标签查不到配置，不能因商品编号复用而生效。
- 完整数据库复制仍继承来源和公开标识；停止旧实例后迁移可保持标签有效。若用于运行独立实例，应更换来源并重新生成标签；两份数据库的计数不提供跨实例共享。

## 10. 实施拆分

1. 服务端：抽取公共开单逻辑，新增配置与明细表、整组编辑接口、预览与多商品原子执行，补齐权限、归属、商品删除及备份恢复规则。
2. 协议：扩展 Web / Android 扫码分类器，保留商品解析器只处理商品类型；复用现有 `qrSymbol` 生成标签。
3. Web：管理列表、多商品明细编辑、整单确认、执行结果与使用记录，接入商品标签页面和扫码工作台。
4. Android：新增多商品配置/二维码展示页面和整组扫码执行流程，保持两端相同默认值、错误处理与重试语义。
5. 文档：更新商品二维码协议、README 扫码行为及设计规范中的确认规则，注明商品标签仍需普通开单确认，业务二维码由配置控制。

服务端与 Web 可以先上线，Android 更新 APK 后使用新类型；功能验收覆盖两端，不将旧安卓客户端视为已支持。

## 11. 验收与必要验证

| 场景 | 预期结果 |
| --- | --- |
| 新建时省略确认配置 | 服务端保存为需要确认；新表单默认开启 |
| A 5 个、B 2 箱、次数 3，成功执行 3 次 | 每次一张含两条明细的单据，只扣一次额度；A 累计变化 15 个、B 6 箱；第 4 次拒绝 |
| 空组合、超过 100 条或重复商品 | 保存拒绝，原有配置与明细不变 |
| 同组合商品来自不同仓库 | 保存与执行均拒绝，不跨仓库更新库存 |
| 添加/移除商品、调整各行数量与价格 | 保存整个组合并递增版本，原标签使用最新明细，已用次数不清零 |
| 默认确认、用户取消 | 单据、库存、已用次数均不变 |
| 关闭确认后主动扫码 | 无额外确认弹窗，全部商品统一执行，生成一张单据 |
| 同一画面重复回调 | 一轮扫描最多发起一次业务执行 |
| 最后一次额度并发执行 | 最多一个新单据成功，无超额消耗 |
| 任一明细库存不足、入库后超上限、行金额或总金额越界 | 全部商品变更回滚，不生成单据、不扣次数，并指出失败商品 |
| 前一商品已更新库存、后一商品更新失败 | 事务回滚前一商品的库存与成本，全部商品保持执行前状态 |
| 多商品确认页 | 展示全部明细、各自数量/单位及总金额，一次确认整张单据，不支持部分勾选执行 |
| 响应丢失、同一请求重试或应用恢复 | 返回原单号，仅一次库存变化和次数消耗 |
| 相同 token 换一个请求标识 | 仍返回原单据，不执行第二次 |
| 预览后配置/确认方式发生变化 | 旧预览拒绝执行，按最新规则重新预览 |
| 已用 2 次，将上限改为 5 / 1 | 改 5 后剩余 3；改 1 拒绝；计数不清零 |
| 商品条码/单位变化、往来单位停用 | 拒绝执行，提示管理员核对配置 |
| 编辑后扫描原标签 | 读取最新商品组合、各行数量/价格、额度和确认方式，历史记录保留完整原明细快照 |
| 员工管理配置、未登录执行、跨仓库引用 | 服务端拒绝；员工可正常执行有效二维码 |
| 错类型、错来源、错模式、普通商品标签增加执行字段 | 不触发库存变更 |
| 作废或退货 | 沿用现有纠正流程，不返还使用额度 |
| 备份恢复、重置后扫描旧标签 | 无法执行；恢复保留完整商品组合与关联记录，需管理员启用并重新打印 |
| 普通扫码、普通开单、旧安卓客户端 | 原流程可用；旧客户端明确拒绝新业务类型 |

服务端测试重点覆盖多商品原子性、整组编辑、并发、幂等、权限及备份兼容；Web 浏览器测试覆盖组合增删、各行数量与价格、默认整单确认、取消、免确认、旧标签与重复回调。Android 验证明细卡片、原生扫码、整单确认弹窗、相机关闭、应用中断后的请求恢复及逐商品错误反馈。实施后执行现有相关测试与构建，确认普通开单和成本计算没有回归。
