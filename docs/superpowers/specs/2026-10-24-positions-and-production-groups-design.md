# 岗位权限与生产组方案

日期：2026-10-24

状态：用户已确认实施；本次实现岗位配置，生产组与派单为后续阶段。部署启动时自动迁移，完成标记与迁移数据同事务提交，之后不重复迁移。

## 已确认的需求

- 权限配置到岗位，员工通过选择岗位取得权限，不再逐人勾选。
- 每名员工一个岗位。
- 每名员工最多属于一个生产组，生产组可不选。仓管、财务等岗位不必属于生产组。
- 后续希望将生产单指派给生产组，组员只能看到本组生产单并进行登记。
- 桌面 Web、移动 Web 和 PWA 共用规则，按仓库约定在 main 提交和推送。

## 推荐结构与备选方案

推荐独立维护“岗位”和“生产组”：岗位决定允许的操作，生产组决定生产单的数据范围。同一个生产员工岗位可以供多个生产组使用。

备选一是将岗位和生产组合成“生产一组员工”“生产二组员工”等配置；初期直接，但每组都要重复维护权限，后续组员调动容易混淆授权。

备选二是支持多岗位、多组并计算权限并集；适合大量兼岗，但当前没有此需求，会增加权限解释、冲突与测试成本，因此本次不采用。

## 第一阶段：本次实现岗位配置

### 管理界面

- 系统设置新增“岗位配置”，可新增、改名、编辑说明、配置权限和查看关联员工人数。
- 沿用当前 13 个业务权限模块；本阶段不改变生产单模块的操作范围。
- 岗位名称去除首尾空格后必填，最多 60 字且不得重名；说明最多 200 字；权限必须来自现有允许列表且不重复。
- 岗位列表显示名称、权限摘要和关联员工人数；空列表提示先新增岗位。
- 用户管理保留“管理员 / 员工”账号类型，并为员工增加“岗位”选择。
- 新建员工必须选择岗位；管理员无需岗位，继续拥有全部权限。
- 员工行将“权限配置”改为岗位选择及“查看权限”，查看的权限只读；修改统一到岗位配置完成。
- 岗位保存前显示受影响员工数，明确保存会同步影响所有关联员工。
- 仍有关联员工（包括已停用账号）的岗位不能删除，需先调整员工岗位；本阶段不增加含糊的岗位停用状态。
- 桌面保持表格和清晰操作分组，窄容器和手机使用可换行布局，按钮文本保持完整、触控目标满足现有移动控件规格。

### 权限与会话

- 新增岗位表，保存名称、说明、权限列表、配置版本、创建及更新时间。
- 用户关联一个岗位 ID，账号类型仍使用现有 admin / employee，不将岗位名称写入 role 字段。
- 每次请求由服务端读取员工当前岗位并计算有效权限；向客户端继续返回现有 permissions 数组及 legacy_permissions 字段，保持业务模块判断接口稳定。
- 岗位权限更新和员工换岗使用版本校验、事务及审计记录，防止多人编辑互相覆盖。
- 岗位权限变化时递增关联员工的 permissions_version；换岗时也递增，利用现有用户数据修订通知刷新页面。
- 后端从下一次请求开始执行新权限；已打开页面通过现有刷新机制更新，不能依赖页面是否已隐藏按钮判断权限。
- 新员工、管理员降级为员工必须选择有效岗位；员工升为管理员时清除岗位关联。最后一个有效管理员保护规则不变。
- 无效或缺失岗位不能恢复历史权限，按无额外业务权限处理并要求管理员修复。

### 既有账号迁移与兼容

- 升级时按“相同权限集合 + 相同旧权限模式”将现有员工归入自动生成的迁移岗位；管理员不分配岗位。
- 空权限员工归入只读岗位，保留物料、库存、历史单据、扫码查询及修改本人密码等既有基础能力。
- 历史 legacy_permissions 员工不能简单转换成同名完整权限模块，因为历史权限有额外限制。迁移岗位保留旧权限兼容标记，升级不扩大或削减既有能力。
- 旧权限迁移岗位只改名称或说明时保留兼容标记；修改权限需明确确认切换为标准模块权限，保存后清除兼容标记，相关成员一起切换。
- 迁移具备幂等性，在事务内完成；失败回滚，不修改账号密码或历史开单人。
- 原逐人权限写入接口返回明确冲突提示，要求刷新并在岗位配置中修改，不能把旧版逐人提交悄悄变成整岗修改。
- 原账号改名、启停接口在未提交岗位字段时保留现有关联；旧客户端若新建员工缺少岗位，返回可理解的校验提示。
- 岗位属于账号配置，业务重置和业务备份恢复不覆盖岗位及用户关联；完整数据库备份仍包含这些数据。

### AI 助手同步

- AI 继续根据服务端计算的有效业务权限判断工具可用性。
- 岗位权限变化或换岗需使旧会话授权上下文和待确认动作失效，防止沿用变更前权限执行。
- 本阶段不增加 AI 管理账号或岗位的工具；检查 server/ai.js、src/AiAssistant.jsx 和 tests/ai.test.js 的权限说明与变更测试。

### 第一阶段验收

1. 新增岗位、编辑权限、分配给多名员工；一次岗位修改对所有成员生效，其他岗位不受影响。
2. 既有登录会话无需重新登录即可按新权限接受或拒绝请求；刷新后页面操作入口一致。
3. 员工不能创建岗位、调整本人岗位、修改岗位权限或管理其他账号。
4. 并发编辑返回冲突，不覆盖新配置；名称重复、无效岗位、未知权限均有明确提示。
5. 有成员岗位不能删除；无成员岗位可删除；管理员降级、最后一个管理员保护不退化。
6. 空权限、显式权限及旧版员工迁移前后的有效能力一致，重复启动不重复生成岗位。
7. AI 权限撤回及换岗后，旧会话和待确认操作不能沿用旧授权。
8. 桌面和移动 Web / PWA 完成岗位创建、编辑、员工分配及查看权限；运行相关 API、浏览器测试与构建。

## 第二阶段：生产组、派单与登记（本次只确定方向）

### 业务关系

- 新增生产组资料和用户的可空生产组 ID；生产组可以包含不同岗位的员工。
- 生产单保存负责生产组 ID，第一版一单一个组；未分配单据留在主管的待分配列表，本组员工不可见。
- 岗位继续承载操作权限，并为生产业务设置“全部生产单 / 本组生产单”的数据范围。
- 生产主管可查看当前仓库全部生产单并派单；生产员工只能查看当前仓库指派给本组的单据。
- 仓管无需加入生产组，可依入库/出库权限处理各组的材料单和成品入库单。这不自动授予全量生产单详情或生产登记权限。
- “本组”范围的员工如果没有生产组，生产列表为空、无法登记；不能把空组当成全部数据。

### 操作权限拆分

现有 production 权限覆盖开单、改计划、开始生产、申请材料和登记等操作，不能直接分配给只负责登记的组员。进入第二阶段时拆分并迁移为明确能力：

| 能力 | 建议典型岗位 | 范围 |
| --- | --- | --- |
| 查看生产单 | 主管、组长、生产员工 | 岗位配置为全部或本组 |
| 生产计划管理 | 主管 | 建单、改计划、结束生产 |
| 生产派单 | 主管 | 分配或改派生产组 |
| 生产执行 | 组长或获授权员工 | 开始生产、申请领补退料；本组或全部范围内 |
| 生产登记 | 生产员工、组长 | 在已获准生产的单据登记产量、耗料、废料及原因 |
| 生产纠正 | 获授权主管 | 现有作废条件仍须满足；回退已入库批次还需入库权限 |

登记权限不能顺带允许更改计划、改派、结束或作废。隐藏按钮和服务端路由校验都需要按上述能力拆分；尤其目前批次登记请求可以同时携带结束生产意图，后端必须独立校验结束能力。

生产登记继续生成待仓库批准的成品入库单，不直接替代仓库入库审批。具体岗位勾选哪些细分操作在第二阶段实现前按实际流程确认。

### 数据隔离的实现边界

- 建立统一服务端生产单授权规则：必须同时满足功能权限、当前仓库以及岗位允许的数据范围。
- 列表查询的 WHERE、总数和分页同时带生产组范围，禁止先查全部再由前端过滤。
- 详情、批次登记、材料申请、开始/结束、取消、作废等接口都校验生产单归属。非授权详情按不存在处理，不能靠猜 ID 越权。
- AI 的 listProductionOrders/getProductionOrder 调用也必须携带授权上下文；目前两函数只有仓库范围，需要同步调整。
- 物料历史、相关单据、统计、通知内容和导出不得泄露本组范围外的生产明细；仓管审批只返回其工作所需字段。共享物料及库存总量仍保持现有共享规则，生产明细按范围限制。
- 换组、岗位范围变更和生产单改派都必须重新校验已打开详情和提交请求；授权变更更新版本，旧响应不得重新填回页面，AI 历史上下文不能继续带入越权生产数据。
- 生产组权限不会单独收回曾经合法展示或用户自行下载的信息；应用内存、离线草稿和缓存必须避免继续提供已撤权生产记录。当前 PWA 草稿是入出库单，不应为了此功能无差别删除其他业务草稿。

### 派单与历史

- 第一期派单建议只允许未开始生产的单据直接改派；进行中转组需后续明确交接规则，不能只改组 ID。
- 历史未分组生产单默认仅主管可见，不默认向全体组员开放。
- 登记保存实际员工 ID、姓名快照、登记时生产组 ID 与名称快照、时间；以后员工换岗换组不改写历史责任人。
- 生产组改名不破坏单据归属；存在未结束单据的组不可删除或停用。
- 第二阶段需制定生产组和派单关系的业务备份迁移与恢复映射：跨实例恢复不能按相同数字 ID 自动绑定本地组；无法可靠映射的单据应未分配并由主管确认。
- 第二阶段验收至少覆盖跨组列表/详情/写入、未分组员工、未派单、仓管无组审批、AI 查询、物料历史和改派/换组后的旧页面提交。

## 实现边界

本次第一阶段完成岗位配置、员工选岗、既有权限迁移和权限生效验证；不提前创建空生产组表、不修改生产单可见范围，也不宣称已支持仅登记岗位。第二阶段以本稿关系模型为基础另行实现生产组和派单。

建议改动集中于独立岗位权限服务、server/auth.js、shared/permissions.js、用户及岗位界面、设置入口、数据修订与 AI 授权测试。避免无关业务重构。
